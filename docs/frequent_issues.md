# Frequent Issues & Known Fixes

A running registry of every issue we've diagnosed and fixed across the DFS base — data, automations, and interfaces — so the same root cause never gets re-diagnosed from scratch twice.

**Two purposes, in order:**

1. **Diagnostic sweep.** Run this list top to bottom against the live base (Sandbox first) to check whether each known issue class still shows up anywhere it hasn't been fixed yet, and apply the documented fix if so.
2. **Pre-launch gate.** Before shipping *any* new interface, automation, or field to Production, check it against this doc — most of these are recurring bug *classes* (a wrong field reference, a stale filter, a deprecated appointment-type field), not one-off typos, and the same class shows up in a different file every time it isn't checked for up front.

Keep this file current: every time a new issue is diagnosed and fixed, add a row (or update an existing one if it's a repeat of a known class). Source of truth for the raw tracker items this was compiled from is the Feedback Tracker / [Julia OOO Tracker artifact](https://v0-singular-artifacts.vercel.app/artifacts/1b69963d-3a0d-45e1-a116-3b9682051ef8); this doc is the durable, dev-facing distillation of it — write here in terms of the underlying bug class, not the tracker's item numbering, so it stays useful after the tracker itself is archived.

## Recurring bug classes (check these first, on anything new)

These aren't single bugs — they're patterns that have each caused multiple independent issues across different interfaces. Any new interface, automation, or field touching the same territory should be checked against these explicitly before launch.

- **Deprecated/wrong field reference.** Several stage-sync and appointment-type bugs traced back to an automation or interface reading a field ID that used to be correct but was superseded (e.g. an old appointment-type field, a filtered "next appointment" lookup instead of the unfiltered one). Whenever a field is deprecated, grep the whole repo for its field ID before assuming nothing still depends on it.
- **`useRecords(table, {fields: [...]})` field restriction.** Calling `getCellValue()`/`getCellValueAsString()` on a field not included in that array returns null/empty even if the field has real data — looks exactly like a sync bug but is a code bug. Check the field-load list first whenever a linked/lookup field reads as empty.
- **Date handling (month/day swap, ±1-day timezone shift, format-mismatch comparisons).** Full rulebook: [`docs/date_handling_rulebook.md`](date_handling_rulebook.md). Any new date display, filter, or sort must be checked against it — this bug class has recurred independently on at least 11 interfaces.
- **`STAGE_ORDER`/`STAGE_STEPS` duplication.** Interface Extensions run isolated per file, so pipeline-stage constants are copy-pasted across `pipeline.tsx`, `alterations.tsx`, etc. A stage definition change made in one file silently doesn't apply to the others unless updated by hand everywhere. See [`docs/phase_logic_rulebook.md`](phase_logic_rulebook.md).
- **Percent-formula fields return decimal fractions via the API**, not 0–100 integers. Any automation or interface comparing against "100%" must compare against `1` with epsilon tolerance, not `100`.
- **Bride-level fields that are actually per-order.** Fulfillment Method, Client Notified, Tracking #, 3PL, Pick Up/Ship status were all originally modeled at the bride level and broke for any bride with more than one order. The fix pattern each time was the same: replace the single field with an inline per-order table. Any new field describing "status of an order" belongs on the order, not the client, from the start.
- **Native `<select>`/`<option>` styling.** A `<select>`'s `color`/background CSS cascades into its native `<option>` popup unless explicitly overridden per-option — looks like "dark mode is broken" but is a plain CSS inheritance issue. Fix: style `select option` explicitly, and use `box-shadow` (not `outline`) for focus rings on pill-shaped controls, since `outline` ignores `border-radius`.

## How to run the diagnostic sweep

1. Work through the **recurring bug classes** section above first — grep the current codebase for each pattern (deprecated field IDs, `useRecords` field-restriction lists, date parsing/formatting, bride-level fields that should be per-order, native `<select>` styling) rather than waiting for a bug report.
2. For each interface or automation touched, check the **known issues & fixes** table for any row in the same area (e.g. touching Appointments → check every Appointments row here, not just the one that prompted the change).
3. Log anything newly diagnosed as a new row here, written as the underlying bug class where possible (not just "fixed issue #N") so it stays useful once the source tracker item is closed and forgotten.
4. Before merging anything into Production, re-check the row(s) relevant to what changed — a fix applied to one interface does not automatically apply to a sibling interface with its own copy of the same logic (see `STAGE_ORDER` duplication above).
