# Refund Requests

Group: Daily Ops · File: `refund_requests.tsx`

> See [`docs/CROSS_CUTTING.md`](../../../docs/CROSS_CUTTING.md) for rules shared across interfaces (Cobalt boundary, dark mode, sandboxing, etc.).

## Business Objective

Track a refund/settlement request from the moment a client's issue is logged through internal review, approval, and final settlement close-out — giving staff a working "Requests" list for daily use and a dedicated "Review" board for triaging new cases, the same two-layout split as `customization_requests.tsx`.

- `Orders - Shopify` (`tblHFGbijtvZcRPkE`), `Order Items` (`tblWOBS5nX0GZokaU`), `Clients`/`DF Clients` (`tblLLUlDgJ4ktzF7c`).

## Outputs

- Two toggleable layouts, switched via `LayoutDropdown` (fixed-width, no chevron, per Axel 2026-09-02):
  - **Requests** — a flat table (Client, Order, Category, Request Stage, Proposed Resolution, Approved Resolution, Settlement Stage). Default filter hides cases that are both `request_stage = "Approved"` and `settlement_stage = "Closed"`; "Show All" toggles that off.
  - **Review** — a two-column kanban board: "New Requests" (`request_stage = "Requested"`, draggable) and "Under Review" (`request_stage = "Under Review"`, drop target). Dragging a New Request card onto Under Review writes `request_stage: "Under Review"`.
- A `DetailPage` per request with the full field-edit/approve/reject/close flow.
- A "New Refund Request" creation modal.
- A Feedback button/modal writing to the shared Feedback table.
- Both layouts and the kanban's two columns each scroll independently (`overflow-y-auto`/`overflow-auto`) inside a fixed `h-screen` root — the page/document itself never scrolls — and both table headers are `position: sticky; top: 0` inside their own scroll container.

## Workflow

1. **New Refund Request**: staff pick a Client (search-to-select, filtered — see Rules), then an Order belonging to that client, then Refund Category and Proposed Resolution. Refund Details (free text), the "product-specific" toggle, and Order Items are all optional. If the selected order has no `order_items` records at all, the product-specific toggle is hidden and a note explains the refund will be treated as an order-level charge instead. Submitting creates the record with `request_stage: "Requested"`, `client_email_sent: false`, a generated `case_name` (`"{Client} — {Category} — {today's date}"`), and opens straight into that record's Detail Page.
2. **Product-specific toggle**: "No, order-level" / "Yes, product-specific" — a two-state button, not a checkbox, backed by `is_product_specific`. Turning it on reveals a search-to-add dropdown (placeholder-only, never shows the current selection — already-added items are excluded from its list) and, once at least one item is added, an Order Items table (ID / Style / Amount, remove control as the last column) below it. Turning it off clears any selected order items.
3. **Requests layout**: search by client name, filter by Category/Request Stage/Resolution Type/Settlement Stage (grouped into a collapsible filter-funnel button once they don't all fit the toolbar width), sorted by each field's own live choice order (Request Stage first, then Settlement Stage) rather than alphabetically. Clicking a row opens its Detail Page with `sourceLayout: 'requests'`.
4. **Review layout**: two static columns, no filters/search-bar row beyond the shared search box. Clicking a card opens the Detail Page with `sourceLayout: 'review'`.
5. **Detail Page actions**, gated by `sourceLayout`:
   - "Move to Under Review" only shows from Review when `request_stage = "Requested"`.
   - Approve / Reject / Cancel only show from Review when `request_stage = "Under Review"`. Approve opens a confirm dialog to pick the Resolution Type (defaults to the proposed value); confirming sets `request_stage: "Approved"`, `resolution_type_approved`, and `settlement_stage` to `"Refund Pending"` (Direct Refund) or `"Discount Pending"` (any other resolution).
   - "Mark as Closed" shows whenever the request is Approved and its settlement is still Pending; sets `settlement_stage: "Closed"`.
   - A Sales Associate opening a case from the Requests layout never sees any of the above four actions — same `sourceLayout` gating pattern as `customization_requests.tsx`'s internal Approve/Deny.
   - Fields (Client/Order/Category/Proposed Resolution/product-specific toggle+items/Refund Details) are editable only while `request_stage` is `"Requested"` or `"Under Review"` **and** the user has update permission; otherwise the page renders a read-only version of the same layout.
6. **Deep links**: a `?record=recXXXXX` URL param jumps straight to that record's Detail Page on first load, choosing `sourceLayout: 'review'` if the record is Requested/Under Review, otherwise `'requests'`.
7. Every field write (client/order/category/resolution/product-specific/order-items/reason/stage transitions) is serialized through a per-record write queue so overlapping edits don't race; a concurrent-edit banner appears if the record's stage/resolution/reason values change underneath the open page, with a "Reload" action to resync.

## Rules

- **Client picker exclusion, twice-revised (2026-09-01/02):** the New Refund Request and Detail Page client pickers both require the client to have at least one linked `Orders - Shopify` record (`clientIdsWithOrders`, built from `ORDERS_FIELD_IDS.CLIENT`) **and** exclude clients whose `Clients:stage` is the "Fulfilled" choice (`CLIENT_STAGE_FULFILLED_CHOICE_ID = 'sel9gJfBcN2v0VLTc'`) or the "Did Not Convert" choice (`CLIENT_STAGE_DID_NOT_CONVERT_CHOICE_ID = 'seljgOGavG7lL15Sl'`). Both are matched by the choice's stable id, not its display name, because Axel plans to rename "Fulfilled" to "Closed" — matching by id means that rename won't silently break the filter. "Did Not Convert" was originally meant to stay selectable (2026-09-01) but Axel reversed that decision the next day (2026-09-02) to also exclude it.
- **Detail Page always force-includes the record's own client**, even if that client no longer qualifies under the rule above (e.g. their stage moved to Fulfilled after the request was filed) — otherwise the picker would silently blank out a real, already-linked client. See the `currentClientId` special-case in `clientOptions` in `DetailPage`.
- **Order label perf fix (2026-09-01):** every order label ("#<ShopifyOrderNumber> — <item style names>") reads `Orders - Shopify:order_items_style` (`fld38iuxvuEVYOhZ6`, a rollup of unique `order_items.style` values) directly, via `buildOrderLabel()`. It previously scanned the whole `order_items` table per order (O(orders × items), ~39M `getCellValue` calls through the SDK) and hung the page on every "New Refund Case" click or record open. Falls back to the order's own `Items` link field (`fldZHRtwkWdIWCrpF`) only when the rollup is empty. Per-row Order Items table labels still read `style`/`name_if_no_style` directly off each `order_items` record (`getOrderItemLabel()`) — that per-row read is fine since it only runs over one order's items, not the whole table.
- **Category chips (`CategoryChip`) use a fixed rainbow palette** (`RAINBOW_PALETTE`, Airtable's real Light1-tier single-select hex values, e.g. `#9CC7FF` blueLight1) cycling by each active category's sorted-alphabetical index — not a synthetic evenly-spread HSL hue. This exists because `refund_category` is a linked record, not a single-select, so there's no live Airtable choice color to read for it. The palette is reused verbatim in `draft_orders.tsx` and `sold_orders.tsx`'s read-only Refund Case panels — don't diverge it there without updating all three.
- **Stage/resolution chips (`StagePill`) read live choice colors** from each field's own `config.options.choices` via `getChoiceColorHex()` — a complete Airtable Light2/Light1/Bright/Dark1 color-name → hex map (an earlier version only covered Light2+Dark1 and silently fell back to gray for any field using a Light1/Bright choice color, which `request_stage`/`settlement_stage`/`resolution_type` all do live).
- **Required vs. optional fields to create a request:** only Client, Order, Refund Category, and Proposed Resolution are required (`canSubmit`/`handleNewCaseSubmit`). Refund Reason (Refund Details), the product-specific toggle, and Order Items are all optional — an order with no item-level data on file is expected and handled (soft banner instead of a blocked toggle).
- **Detail Page's stage/info panel (right column) is a `surface`/white bordered card**, matching `draft_orders.tsx`'s actual Summary/Refund Case panel treatment — not the flat sandy `panel_bg` tone this page used before Axel's 2026-09-02 follow-up (that tone is kept in the token set only for a possible future need, see the comment on `panel_bg`). Each label+chip row is inline (`justify-between items-center`), and the label is one Tailwind tier above its chip (`text-lg` label vs. `text-base`/`size="lg"` chip) — this `size="lg"` prop only exists on this one panel; every other `StagePill`/`CategoryChip` usage (table cells, the read-only content column) stays at the default `size="sm"`/`text-sm`.
- **Zebra striping (`table_zebra`/`table_header` tokens) is scoped to this file only for now** — odd rows tint to `table_zebra`, even rows fall through to plain `surface`, and the header is one notch darker than the zebra tone so the visual order is always header > zebra > white. Axel's ask is to bulk-roll this out to the other daily_ops files in a later pass; don't assume `draft_orders.tsx`/`customization_requests.tsx`/`sold_orders.tsx` already match this until that pass lands.
- **"Go back" button standardized (2026-09-02)** to `pipeline.tsx`'s reference treatment (white/`surface` card, 1px border, `0 1px 3px rgba(0,0,0,0.05)` shadow) instead of a plain text-link style — this file, `draft_orders.tsx`, and `customization_requests.tsx` all now share this exact button. The Detail Page's header row is also wrapped in the same `max-w-4xl mx-auto` the content grid below it uses, so the back button's left edge lines up with the content instead of sitting further left via a bare `px-6`.
- **Page-level scroll containment (2026-09-02):** the root is `h-screen overflow-hidden` (a ceiling, not `min-h-screen`'s floor) with only the toolbar-below region carrying its own `overflow-y-auto`/`overflow-auto` — verified against 55 "TEST — Scroll Sample" records in the sandbox base for both the Requests table and the Review board, which previously scrolled the whole document (toolbar included) once content overflowed the viewport. Table headers are `position: sticky; top: 0` inside those same scroll containers.
- **Filter-group popup and the New Refund Request's Order Item dropdown never use `overflow-hidden`** on their containers — each filter/dropdown renders its own child popup, and clipping the container would cut those popups off too.
- **Feedback subsystem** mirrors `draft_orders.tsx`'s pattern (writes to `tbluy7JS31NwCoeIi`, scoped by `tblG92AI3ddzlolhz` Interface/Page records) minus Attachments — there is no attachment field or UI in this instance, per scope.
- Field labels on the product-specific toggle and the Order Item search dropdown are read live off the field object's own `.name` (`isProductSpecificFieldName`/`orderItemsFieldName`), not hardcoded strings, so a future Airtable field rename stays in sync automatically.
