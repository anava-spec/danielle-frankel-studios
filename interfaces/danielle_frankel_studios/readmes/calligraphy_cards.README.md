# Calligraphy Cards

Group: Tracking · File: `calligraphy_cards.tsx`

> See [`docs/CROSS_CUTTING.md`](../../../docs/CROSS_CUTTING.md) for rules shared across interfaces (Cobalt boundary, dark mode, sandboxing, etc.), and [`docs/date_handling_rulebook.md`](../../../docs/date_handling_rulebook.md) for how this file's date parsing/comparison/formatting must work.

## Business Objective

Give the internal team a single list of every client's calligraphy card status, alongside due date, wedding date, and order info, so they can prioritize who's next, plus a detail popup per client for the full record and for advancing the card through its production steps. Internal-only, not client-facing.

## Inputs

- DF Clients table (`tblLLUlDgJ4ktzF7c`) — read directly, no separate Calligraphy Cards table exists.
- Fields used: `Full Name`, `Due Date` (formula), `Items Sold` (lookup), `gown_name` (lookup), `Dress Creation Year`, `Wedding Date (Formatted)`, `calligraphy_card_sent` (singleSelect), `calligraphy_card_comments` (long text).
- Generated via Omni from an Omni prompt spec, then rebuilt in-house for branding compliance and fixed once discovered to be the wrong field type (see Rules below).

## Outputs

- A list page in the Tracking section showing every client with a Status pill, Client, Due Date, Items Sold, Gown, Dress Year, and Wedding Date. Clicking a row opens that client's detail popup.
- The detail popup's title bar shows the client name and a "Move to next step" action; the body (a single unsectioned box directly under the title bar) shows the full status flow as a horizontal stepper, Wedding Date/Due Date/Gown/Dress Year, Items Sold as plain text, and Comments.
- Writes back `calligraphy_card_sent` (from the list's Status pill, or the popup's Move-to button) and `calligraphy_card_comments` (popup only) — every other field is read-only display.

## Workflow

1. **Qualification floor (always-on, not a filter toggle):** a client only ever appears on this list if `Item Category` (`fldE4AX5gz8pwah4j`) contains at least one category that is **not** shoes or veil, OR has no `Item Category` at all (no orders — see the visible Items Sold filter below, which now owns that case instead). A client whose `Item Category` is exclusively shoes/veil never qualifies. Approved deviation from the original AC: "direct-to-consumer" isn't a separate flag on `DF Clients` yet, so for now this is the only DTC-qualification signal. `Item Category` is itself a lookup through `shopify_order` (a link field) — same nested-structure quirk as Items Sold/Gown, resolved via `unwrapLinkedNames()`, never `getCellValueAsString()`.
2. Filter bar order: Search (long, always-expanded) → Due Date → Wedding Date → Calligraphy Status → Items Sold toggle.
   - **Items Sold toggle:** a plain two-state button (not a clearable dropdown) — "Hiding Empty Items Sold" (default) hides any client whose Items Sold is blank; "Showing All" shows them too.
   - **Calligraphy Status filter options are read live from the field's own Airtable choices** (`getFieldChoices`) — never hardcoded — so adding/renaming/reordering a choice in Airtable is reflected here automatically, no code change needed.
3. Search is a non-narrowing typeahead: typing never filters the visible list — it shows a dropdown of matching client names, and selecting one narrows the list to that single client.
4. Wedding Date filter: "Upcoming Wedding Dates" vs. "Past Wedding Dates" — clearable (X), no filter applied when cleared (shows every wedding date, including blanks).
5. Due Date filter is an exact-date match, compared as local `YYYY-MM-DD` strings (never UTC ISO).
6. All active filters compose with AND logic, on top of the qualification floor; sort is Wedding Date ascending (blanks last), then Client name A→Z.
7. Clicking anywhere on a row (other than the Status pill) opens that client's **detail popup** (`ClientDetailModal`) — a modal, not full-page navigation (corrected 2026-07-30; the first version wrongly used a full-page pattern like `did_not_convert.tsx`'s client detail).
8. On the list, clicking the Status pill opens a small dropdown (`StatusPillDropdown`) listing every status as a colored pill option — the user picks the value explicitly. In the detail popup, status only ever advances one step forward via the title bar's "Move to next step" button (see Rules) — the dropdown on the list is a faster path for correcting a status directly, the popup enforces the sequential flow.

## Rules

- **Fixed 2026-08-26 (date_handling_rulebook.md R-05/R-06):** the Due Date exact-match filter, the Wedding Date Upcoming/Past filter, and the Wedding Date sort comparator all used to round-trip a date-only value through `new Date(value)` + local getters/epoch-ms diff for comparison — the same timezone-shift bug class `formatDate()` was already fixed for display on 2026-08-22, just hitting the filter/sort paths instead. A viewer west of UTC could see the exact-date filter return the wrong day (confirmed live: filtering "Aug 13" returned records dated "Aug 14"), and a wedding happening the same calendar day as "today" could drop out of "Upcoming" a day early. Replaced with `dateOnlyKey()`, which extracts the `YYYY-MM-DD` prefix directly (no local-timezone `Date` construction) — safe because ISO date-only strings compare/sort correctly as plain text. The sort's behavior is unchanged (lexicographic order on zero-padded ISO strings is mathematically identical to chronological order); only the exact-date and Upcoming/Past filters actually change behavior. **Also discovered live while testing this fix, against the full ~7,600-record production dataset:** `getCellValue()` on a date/formula-date field is NOT reliably a string. It crashed twice during testing on 2026-08-26 — first as a native `Date` object (this file's formula-derived Due Date field, reproduced on a freshly-created test client, not on older cached records — same SDK quirk already handled elsewhere in this codebase via `.toISOString()`, see `unwrapLookupValue` in `pipeline.tsx`/`alterations.tsx`/`did_not_convert.tsx`), then again on some other malformed legacy value once the Wedding Date filter was cleared and the full dataset was evaluated. Both `dateOnlyKey()` and `formatDate()` now go through a shared `toDateOnlyString()` normalizer that only ever returns a genuine string or a valid `Date`'s own `.toISOString()` (UTC — a date-only value from this SDK is anchored at UTC midnight, so reading it back via its own UTC ISO string recovers the correct calendar day; local getters would reintroduce the timezone-shift bug this fix exists to prevent) — anything else (an invalid `Date`, or any other shape) returns `''` rather than throwing, so one bad legacy record can never crash the whole page again.
- Dark mode uses the canonical pattern (`fulfillment.tsx`'s approach): plain Tailwind `dark:` utility classes driven by `useColorScheme()` toggling a `dark` class on `document.documentElement` — reads Airtable's own theme setting, not the OS/device theme. No bespoke token object.
- **Status choices and colors are never hardcoded (2026-07-30).** `getFieldChoices(field)` reads the field's real Airtable choices (name + color, in schema order) directly from `field.options.choices` — used for the list's Status pill dropdown, the Calligraphy Status filter, and the popup's `StatusStepper`. `getFieldChoiceColorMap` is now derived from `getFieldChoices`. Schema order matters specifically because it drives the sequential "advance to next" flow below — don't reorder choices in Airtable without checking that the intended step order still holds.
- **Confirmed 4-step flow (2026-07-30 stand-up):** `Pending` → `Production Approved` → `Sent to Calligrapher` → `Received from Calligrapher`. Production approval (Margo signing off on the card content) is a distinct step from physically sending it; "received" tracks the card coming back from the calligrapher.
- **The detail page is a popup (`ClientDetailModal`), not a full page (corrected 2026-07-30).** Fade+scale in/out per BRANDING.md §12, 720px-class width, closes via backdrop click or Escape only — **no X close button** (removed 2026-08-03, by request; the popup's only affordances are backdrop/Escape and the title bar's advance action) — no "Go back" button either (there's nowhere to navigate back to; a modal doesn't need page-style back nav). **Height defaults to `h-[60vh]` (capped at `max-h-[90vh]`, 2026-08-04)** — previously it only had the `max-h-[90vh]` cap with no default height, so it sized itself purely to content; now it's 60% of the window height by default regardless of content length, still never exceeding 90% of the window height.
- **Title bar holds both the client name and the advance action, labeled "Move to next step"** (renamed 2026-08-03 from "Move to X"/`Move to "{nextChoice.name}"` — the button no longer names the destination status, just that it advances). Only ever offers the *next* choice in schema order — there is no way to jump to an arbitrary status from the modal (the list's `StatusPillDropdown` still allows picking any value directly, for corrections). Clicking it opens `AdvanceConfirmPopover` — **a small popover anchored under the button (`absolute right-0 top-full`), not a full-screen modal (corrected 2026-08-03 — no dim/blur backdrop at all anymore)**, local state owned by `ClientDetailModal` itself. Still a deliberately minimal confirmation: one short line of text and a single "Continue" button — **no X, no Cancel, no outside-click-dismiss** (there's no backdrop to catch that click either), by explicit request. This is an intentional deviation from every other modal in this project (which all support backdrop/Escape/X dismissal) — don't "fix" it to match them.
- **`StatusStepper`** renders the full choice list as horizontal dots-and-connecting-line, same visual language as `pipeline.tsx`'s "Stage in pipeline" component on the Full Client Profile — colored from each choice's real Airtable color, resolved to actual hex via `resolveStatusHex`/`AIRTABLE_HEX` (a separate hex map from `AIRTABLE_COLOR_MAP`, needed because the connecting line **progressively gradients** from one step's color into the next's, not just a solid on/off line — flat Tailwind classes can't do that). Light/Bright color tiers escalate to their family's Dark1 for contrast, same convention as `pipeline.tsx`'s own stage stepper. **Stage labels never wrap (2026-08-03):** `whitespace-nowrap`, no `max-w` cap — a stage name always renders on one line even if that widens the stepper.
- **Field titles (not section headers) use the larger `text-sm` size** (`DetailRow`'s label, bumped up 2026-08-03 from `text-xs`) — the stepper's status labels already used `text-sm`. There are no section headers left to size (see next point).
- **Detail modal body has no box at all now — it's flat content directly under the title bar (2026-08-03, second correction).** The first pass (same day) wrapped everything in one bordered/padded box with no sub-section titles; per further feedback, even that outer box was removed — no border, no padding container, just `StatusStepper`, `FieldRow`s, and Comments sitting directly in the scrollable body div (`p-6` from the body wrapper itself, nothing extra). `DetailSection` (the old per-block bordered-card component) stays removed; `FieldRow`/`DetailRow` remain. Layout: `StatusStepper`, then `FieldRow cols={4}` → Wedding Date / Due Date (hover tooltip explaining it's 3 months before the wedding date) / Gown / Dress Year, then `FieldRow cols={1}` → Items Sold **as plain comma-joined text, not pills** (pills are still used on the main list's Items Sold/Gown columns, just not here), then Comments — labeled with a plain field-title div (matching `DetailRow`'s label style) instead of a section header, directly above `CommentsCell`.
- **Comments fills the popup's leftover vertical space instead of leaving it blank (2026-08-04).** The body wrapper is `flex flex-col`; the stepper+fields sit in a `flex-shrink-0` block up top, and the Comments block below it is `flex-1 min-h-0` — so it stretches down to whatever space is left once the popup's `h-[60vh]` default is applied, rather than the popup showing a blank gap under a short comment. `CommentsCell`'s textarea (`flex-1 min-h-0`) still grows taller than that allotted space when its own content actually needs more room: `resize()` clears the inline height (letting flex reclaim the fill-remaining-space size), reads `scrollHeight` vs. the resulting `clientHeight`, and only sets an explicit taller height if content genuinely overflows — re-run on every keystroke and on window resize (since the 60vh popup height, and so the space left for Comments, changes with the window).
- **Comments moved off the main list (2026-07-30):** `calligraphy_card_comments` (`fldfrtzC0BxWggmoU`, long text, snake_case) is edited only on the detail page now — it was on the main table briefly, but per request it belongs on the detail popup instead, to keep the list scannable. Free-text notes for Margo to write name variations to use on the physical card (e.g. "Deanna sees Gemma & Gia Kennedy → card should say Gemma and Gia").
- **Dress Creation Year column:** "Dress Year" sits between Gown and Wedding Date, sourced from `Dress Creation Year` (`fldwgDZDs2CNEqPsQ`) on `DF Clients` — a `Number` field, precision 0. Created via API in the sandbox base (`appMmEE4zyHMGhkkd`). **Still pending: publishing this field from sandbox to production** so it actually has data for real clients.
- Wedding Date is a clearable `SingleSelectDropdown` (BRANDING.md §5) — label acts as its own placeholder when empty; clearing removes that filter's effect entirely, no third "All" option baked into the choice list.
- Date picker reuses `fulfillment.tsx`'s exact `CalendarPopup`/`DatePicker` components (272px panel, Monday-start week, Clear/Today footer) rather than a native `<input type="date">`.
- Items Sold and Gown are plain lookup text values displayed as neutral-gray pills — **but not from a text field**: both lookups (via `shopify_order`) resolve to Orders - Shopify's `Items` field, which is itself a `multipleRecordLinks` field. Their raw cell value is therefore a nested array of linked-record references, not plain strings — resolved via `unwrapLinkedNames()`/`getLinkedNamesDisplay()` (same underlying runtime quirk as `did_not_convert.tsx`'s `unwrapLookupString` and BRANDING.md §9's lookup-color note).
- Never include `import './style.css';` in this file.
- **Wedding Date off-by-one-day bug, fixed 2026-08-22:** `formatDate()` (used for both the list column and the detail popup's Wedding Date row, and incidentally Due Date too, since they share the same helper) fed a date-only cell value (e.g. `"2026-08-23"`, no time component) straight into `new Date(value)` — JS parses that as UTC midnight, which `Intl.DateTimeFormat` then renders in the viewer's local timezone, showing the day before for anyone west of UTC (a wedding on Aug 23 was displaying as "Aug 22, 2026"). Fixed by matching the ISO year-month-day prefix first and building the `Date` from those components directly (`new Date(y, m, d)`, all local) — same fix pattern already used for Wedding Date in Fulfillment/Alterations/Sold Orders/Appointments/Draft Orders. Deliberately did **not** change which field this reads (`Wedding Date (Formatted)`, still no fallback to `Wedding Date (If Not Set)`) — this was a display-parsing fix only, not a field migration.
- **Config-level cause of a past "zero results" bug (found via the `airtable-interface-config-doctor` skill, not by reading code):** `Item Category` wasn't exposed to this page's block config (Data → Fields in the page's right sidebar), so every cell read for it came back `undefined` regardless of code correctness. Fixed by enabling the field, then publishing. **Lesson for future "the code looks right but nothing shows up" reports on this or any other interface**: check the page's field-exposure config before re-debugging the code.
