# Recap

Group: Daily Ops · File: `recap.tsx`

> See [`docs/CROSS_CUTTING.md`](../../../docs/CROSS_CUTTING.md) for rules shared across interfaces (Cobalt boundary, dark mode, sandboxing, etc.).

## Business Objective

Give Sales Associates a daily list of consultation appointments and a place to record each one's outcome immediately after — style selected, customizations, embroidery/paint/lace amount, calculated pricing — so that recap becomes the single source of truth Customization Requests and Generate Proposal both read from, without re-entering anything. As of 2026-08, it also generates the client-facing "Recap Doc" (a printed/PDF summary of the appointment) at the close of a first-consultation appointment, so the client leaves with a clean paper record of what was discussed — separate from, and without the pricing math shown in, the Customization Proposal document.

## Inputs

- `Appointments`, `Clients`, `Styles`, `Customizations`, `Customization Pricing`, `Staff`, `Proposals`, and `resources` tables.
- Fields captured per recap: Customized Style (or two styles for Hybrid), Customizations/pricing selections, Amount of Embroidery/Paint/Lace, Additional Details.
- Recap Doc specifically reads: `Appointments.recap_doc` (`fldNlAu1xqmTEtNZI`, multipleAttachments) and `recap_stage_completed` (`fldJmciXBeZjMCXY1`, checkbox, written only by `attachment_router.js`); each client's Favorite Styles and approved Customization Requests; a shared `resources` record (name `attachments_form_url`) holding the environment-correct attachments-form URL; two lookups on Clients — `consultation_appointment_time` (`fldLQRhGqANVci6BM`) and `consultation_appointment_record_id` (`fldDStVqmJpDDNWMP`), both through a manually-curated "Appointment Records" link — identifying which appointment a Recap Doc belongs to.
- Stakeholders: Julia Collins; Sales Associates (primary daily users, both for recap entry and generating/uploading the Recap Doc).

## Outputs

- The completed recap record feeds Generate Proposal (reads style, customizations, embroidery amount, and calculated price directly) and the Customization Requests interface, which references the same underlying record for its own approval/decision workflow.
- The Recap Doc PDF, once generated and uploaded, is written onto `Appointments.recap_doc` by `attachment_router.js` (not by this interface directly — see Workflow below).

## Workflow

1. `RecapApp` (renamed from `AppointmentsApp`, 2026-08) is the main page: a date-picker header (prev/next day, calendar, "Today" shortcut), a client-name search (typeahead with keyboard navigation, `w-[300px]`), Studio/Sales Associate filters, and a table of that day's consultation appointments (Time, Client, Studio, Wedding Date, Sales Associate, Favorite Styles from Acuity, Favorite Styles from Appointment). Only Consultation-type, non-cancelled, client-linked appointments show.
2. Clicking a row opens `PostAppointmentModal`, where the SA edits wedding date/confirmation, measurement notes, RTW size, Favorite Styles, appointment notes, and uploads measurement/appointment photos.
3. Adding or editing a customization opens the nested `CustomizationModal`: pick a Style (or two, for Hybrid), Customizations/pricing, Amount of Embroidery/Paint/Lace (only shown when a selected pricing row needs it), Additional Details — with a live Order Summary (base price, line items, grand total) throughout.
4. "Generate Proposal" is only enabled once every required input is present (Style, at least one customization, Amount if applicable, a grand total above $0, client, sales associate); its disabled-state title always names exactly what's missing, never a generic error. It is never triggered automatically by saving/editing a recap.
5. **Recap Doc, two-step generate/upload** (the Interface Extensions SDK can't push a local `File` into an attachment field, so this can't be one step): "Generate Recap Doc" (title bar) opens `RecapDocPreviewModal`, which shows a live, paginated preview and a "Generate" button. Clicking it fires `window.print()` (save-as-PDF or a physical printer) and immediately closes the preview, leaving just the print dialog and the appointment detail page. The SA then clicks the "+" button next to the Recap Doc field on the detail page, which opens an external Airtable form (prefilled with client + the target appointment's record ID, every field hidden except the file picker); submitting it triggers `attachment_router.js`, which writes the file onto `recap_doc` and flips `recap_stage_completed`.
6. The title-bar "Generate Recap Doc" button and the field's "+" button are always visible while no Recap Doc exists yet; each grays out and shows a small tooltip **on click only** (not hover) naming the specific blocker — appointment type missing, not a first-consultation appointment, or no Favorite Styles/Customization Requests to include. Once a Recap Doc exists, the title-bar button disappears entirely and the field shows the uploaded file's thumbnail instead of the "+" button.

## Rules

- Hybrid customizations are a single record with two direct Style links (`customized_style` + `additional_customized_style`), not the old parent+2-children model — reworked 2026-07-26. Pricing is `max(baseA, baseB) × 1.85` (the merge surcharge) plus the shared customization line-item total, both priced/Self-Usage'd against whichever style has the higher base price (per Julia, 2026-07-24: "the only difference between hybrid and regular is that hybrid is a merge of two styles").
- Rush Fee / M2M / Alterations checkboxes were removed from the Customizations UI entirely — those now live only on the Draft Order, not here (per Julia's 2026-07-20 demo feedback).
- A multiplier-priced customization line missing its Amount tier shows an "amount *" indicator (red asterisk, hover tooltip) in the Rate column instead of a misleading $0.00.
- `selfUsageField`/`stylesSelfUsageField` are hardcoded field IDs (not fuzzy name-matched) — a 2026-07-27 fix after the previous fuzzy match risked silently colliding with `additional_self_usage` and scaling a fee against the wrong style.
- `parseCurrencyString` handles both US (`1,990.00`) and EU/LatAm (`1.990,00`) number formats — don't assume US formatting when reading a rollup/lookup cell as a string.
- The in-progress "add customization" draft lives in the parent modal's state, not the child's, so dismissing the add modal by accident doesn't lose what was entered — only a successful submit clears it.
- Proposal generation must never occur automatically on recap save/edit — "Generate Proposal" is the only trigger, and must remain visible directly on the recap/customization detail view.
- Recap is functionally and structurally distinct from Customization Requests — don't merge their code paths; Customization Requests is its own page that references the same underlying data for its own approval workflow.
- **Style dropdown (Regular and Hybrid), 2026-08-25:** has no "Favorite Styles in Acuity" scoping (per Julia, 2026-07-24/27), but IS narrowed to customizable styles only (`isCustomizableStyleName` — a case-insensitive "custom" substring anywhere in the style name), same fix as customization_requests.tsx's Style picker. Editing an existing customization keeps its already-linked style(s) visible/selectable even if they don't match the filter, so older records don't silently lose their Style field.
- Never include `import './style.css';` in this file.

### Recap Doc (added 2026-08-03 through 2026-08-05)

- **Pagination is DOM-measured, not chunk-estimated.** `useRecapPageGroups()` renders every entry once into an invisible, normal-flow scratch area, reads real heights via `getBoundingClientRect()` in a `useLayoutEffect`, then packs entries into page groups against a computed usable height (page height − padding×2 − footer height − a safety margin). Each page renders as a plain `816×1056px` block-level `<div>` (US Letter @96px/in), stacked as normal-flow siblings with zero margin — never `position:absolute` "sobre" sections; that approach was tried and reverted 2026-08-04 because it broke pagination back down to one page.
- **The single biggest gotcha, if pagination ever regresses to "always one page":** `RecapDocPreviewModal` portals a SEPARATE `<RecapDocument>` instance straight onto `document.body` (via `createPortal`) — this is the copy that actually prints; the on-screen preview inside the modal body is a different instance with its own independent `useRecapPageGroups()` measurement pass. If the portal's default (non-printing) CSS state is ever `display:none`, its own measurement pass runs on mount while every element inside it measures as zero height (`getBoundingClientRect()` on a `display:none` descendant always returns zero), collapsing everything onto page 1 regardless of what the on-screen preview correctly shows. The portal must stay genuinely laid out at all times — `position:fixed; left:-99999px` off-screen, never `display:none` — with only `position` (not `display`) reset inside `@media print`.
- `@page { margin:0; size:letter; }` must be a top-level CSS rule, never nested inside `@media print` — Chrome registers zero `CSSPageRule` instances (and silently ignores page-size cutting) if it's nested.
- Background colors must be declared on every individual `.recap-doc-page-section`, not a single wrapping container — browsers don't reliably repeat an ancestor's background across a print-fragmented page boundary.
- Each page section is `display:flex; flexDirection:column` with content wrapped in a `flex:1` spacer and the footer outside it, so the footer (logo + page number) sits flush at the true bottom of the page regardless of content height, instead of drifting with it.
- **Typography:** `RECAP_BODY_FONT_FAMILY` is `'Canela Text', 'Fraunces', Georgia, serif` — Canela Text is a commercial font (Colophon Foundry) with no license/webfont source available as of 2026-08-05, so Fraunces (a free, visually similar Google Font) is loaded as an interim stand-in via `ensureRecapWebFontsLoaded()` (injects a `<link>` into `<head>` once on `RecapApp` mount). `RECAP_NUMBER_FONT_FAMILY` (`'Abhaya Libre'`) is genuinely loaded the same way — it's free and actually is the intended font. Swap Fraunces out once Canela Text has a real licensed source (self-hosted `.woff2` + `@font-face`, or an Adobe Fonts/Typekit embed) — 'Canela Text' stays first in the family list so a real license takes priority automatically with no further code change.
- Page padding is `72px` on all sides (`RECAP_PAGE_PADDING_PX`), photo boxes are `84×118px` with a `24px` gap before the text column — both measured directly off a Figma PDF/SVG export (2026-08-04) via PyMuPDF, not guessed from a screenshot. See the `airtable-print-doc-builder` skill (in `singular-tracker/skills/`) for the general technique.
- The Recap Doc shows each style's own **base price only** — never a computed custom/total price. The "Custom Pricing" row was removed entirely (2026-08-05, per Julia): that math belongs exclusively in the separate Customization Proposal document, where the client sees only the final number, not the multiplier.
- Style descriptions on Regular/Hybrid entries currently read `Styles.description` (`STYLES_DESCRIPTION_PLACEHOLDER_FIELD_ID`, `fldjBgzkomQ26lSzV`), a formula field hardcoded to the same lorem-ipsum text for every style — a deliberate placeholder while the "Cobalt" web team builds the real site-to-Airtable description sync. Swap back to the `CUSTOMIZED_STYLE_NOTES`/`ADDITIONAL_CUSTOMIZED_STYLE_NOTES` lookups (or wherever Cobalt's sync lands) once real descriptions exist.
- **The attachments-form URL is resolved live, not hardcoded** — `RecapApp` looks up the `resources` table record named `attachments_form_url` and reads its `url` field (`RESOURCES.URL`), because sandbox and production need genuinely different URLs (same form page ID, different base ID) and regular Airtable records aren't synced between a base's sandbox/production copies. Falls back to `ATTACHMENT_FORM_URL_FALLBACK` (a stale hardcoded URL) only if that record can't be found. Threaded as an `attachmentFormUrl` prop from `RecapApp` down through `PostAppointmentModal` and `CustomizationModal` to every attachment upload call site (`AttachmentSection` ×2, `ProposalPreviewModal`, `ProposalDetailModal`, `openRecapDocUploadForm`) — never re-add a module-level constant for this.
- **The upload form's `prefill_appointment` must be the target Appointment's record ID**, resolved via `CLIENT.CONSULTATION_APPT_RECORD_ID` (a lookup through Clients' manually-curated "Appointment Records" link, unwrapped with `firstLookupValue()` — it's a lookup, always array-shaped even when conceptually single-valued) rather than whichever appointment happens to be open in the modal, since "which appointment a Recap Doc belongs to" is enforced by how that link gets populated (the client's first non-cancelled consultation), not by UI context. An earlier fix wrongly attributed a failed prefill to record-ID matching itself and switched to primary-field display-text matching — the real cause was that the "appointment" field had simply never been added to the upload form; record-ID prefill is correct once the form field exists.
- Client info labels (Email, Phone, Wedding Date, Appointment, Client Specialist) render in literal uppercase text in JSX (matching every other section-label convention in this file), not a CSS `text-transform` — kept consistent with how "APPOINTMENT RECAP"/"STYLES" are already written.
- Blocked-reason tooltips on the Generate/Upload buttons appear **only on click, not hover** (`useClickTooltip()`) — neither button uses the HTML `disabled` attribute (a truly disabled button never fires `onClick`, so there'd be nothing to react to); both style themselves as disabled instead and route `onClick` to either the real action or the tooltip trigger.
