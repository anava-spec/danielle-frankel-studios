## 1. Print pagination — the "always one page" bug

**Symptom (carried in from a prior session):** the Recap Doc's on-screen preview correctly showed multiple pages, but the actual printed/PDF output always collapsed to a single page, regardless of content.

**The breakthrough question:** Julia asked, in Spanish, "¿De verdad se está enviando lo que aparece en el preview o se está enviando otro tipo de data?" ("Is what's printing really what the preview shows, or is something else being sent?")

**Root cause found:** `RecapDocPreviewModal` renders two entirely separate `<RecapDocument>` instances — one visible in the modal body (the "preview" the user judges by), and a second one portaled directly onto `document.body` (via `createPortal`) so print output escapes the modal's `overflow-hidden` ancestor. Each instance runs its own independent `useRecapPageGroups()` pagination-measurement pass.

The portal's default (non-printing) CSS state was `display:none`, only flipped to `display:block` inside `@media print`. Since `useLayoutEffect` runs on mount — as soon as the modal opens, well before any print event — the portal's own measurement pass ran while `display:none` was still in effect. `getBoundingClientRect()` on any element inside a `display:none` ancestor always returns all-zero dimensions, so every entry measured as height 0, and the packing algorithm collapsed everything onto page 1. The separately-rendered, correctly-measured preview instance looked fine the entire time because it's a different mount — but it was never what actually printed.

**Fix:** changed the portal's default state to `position:fixed; top:0; left:-99999px` (genuinely laid out, just off-screen) instead of `display:none`. `@media print` now only resets `position`, not `display`.

**Also fixed in the same pass:**
- `@page { margin:0; size:letter; }` moved to a top-level CSS rule — it was nested inside `@media print`, which produced zero registered `CSSPageRule` instances in Chrome (confirmed live via DevTools), meaning the page-cutting rule never actually applied.
- Background colors declared on every individual page section, not one wrapping container — browsers don't reliably repeat an ancestor's background across a print-fragmented page boundary.
- Border-removal on the last entry in a page switched from a broken `last:` Tailwind pseudo-class (never matched, since entries share their parent with header/footer/grid) to an explicit `isLast` prop.

Along the way, two earlier-session architectural experiments were tried and reverted: a "sobres" (absolute-positioned page sections stacked in one giant sheet) approach regressed pagination back to one page and was reverted to plain block-level page siblings.

## 2. Config-layer diagnosis (config-doctor skill)

Ran the `airtable-interface-config-doctor` skill against a fresh page-config export to rule out config-layer causes before/alongside the code fixes above.

**Finding:** the `resources` table (used for the Recap Doc footer logo lookup) was not declared as a visible table for the Recap page's block in an earlier export — `useRecords()` on an undeclared table silently returns nothing even though `base.getTableByIdIfExists()` still resolves the `Table` object. ## 3. Figma-measured typography and spacing fixes

Julia provided a Figma export (PDF + SVG) since the Figma MCP connector wasn't authorized in this session. Figma exports text as outlined vector paths (no real `<text>` elements or embedded font names), but PyMuPDF (`fitz`) still reads exact per-run bounding boxes and font sizes from the PDF, which is enough to measure real pixel values against the code's constants.

**Three concrete mismatches found and fixed:**
- **Page padding:** every text run's left edge sat at x=72 and every price's right edge at x=744 (816−72) on both pages — true padding is `72px`, not the `32px` (Tailwind `p-8`) previously assumed.
- **Photo box + gap:** Figma's photo placeholder measured `84×118px` with a `24px` gap before the text column; code had `80×96px` (`w-20 h-24`) with a `16px` gap (`gap-4`).
- **Number sizes:** the hand-filled typography spreadsheet called Phone / Style Price / Custom Pricing "identical spec," but the Figma export showed three different sizes — phone 10.5px, style price 13px, custom pricing (later removed, see §7) 11px.

This pixel-diffing technique (PyMuPDF on a Figma PDF export, no MCP connector needed) was generalized into a new skill — see §5.

## 7. Document content changes

- **Footer bottom-anchor fix:** each page section became a `display:flex; flexDirection:column` container with content wrapped in a `flex:1` spacer and the footer outside it, so the logo/page-number footer sits flush at the true bottom of every page regardless of content height — previously it was just the next block-level sibling after the last style row, so its position drifted.
- **Placeholder style descriptions:** per Axel/Julia, Regular/Hybrid entries now read a formula field (`Styles.description`, hardcoded to the same lorem-ipsum text for every style) instead of the pre-existing `CUSTOMIZED_STYLE_NOTES` lookups, purely to preview real layout/pagination with placeholder text while the "Cobalt" web team builds the real site-to-Airtable description sync. Marked clearly as temporary, with the original lookup wiring left in place (unused) for easy reversion.
- **Custom Pricing removed from the Recap Doc entirely**, per Julia's relayed Slack feedback: the document should only ever show each style's own base price, never a computed custom/total price — that math belongs exclusively in the separate Customization Proposal document, where the client sees only the final number, not the multiplier math. Removed the "CUSTOM PRICING" label/value row from both Regular and Hybrid entries, dropped `customPricing` from both entry types and the snapshot builder, and removed the now-unused `RECAP_CUSTOM_PRICING_VALUE_STYLE`.
- **Client info labels uppercased** (Email, Phone, Wedding Date, Appointment, Client Specialist) — matches the Figma export, which never had them in title case.

## 8. Fonts

Neither `RECAP_BODY_FONT_FAMILY` (Canela Text) nor `RECAP_NUMBER_FONT_FAMILY` (Abhaya Libre) was ever actually being loaded — nothing injected a `@font-face` or webfont `<link>` for either, so both silently fell back to Georgia/serif on every machine. Fixed:
- **Abhaya Libre** is a free, open-license Google Font — now self-loaded via a `<link>` injected into `<head>` once on `RecapApp` mount (`ensureRecapWebFontsLoaded`).
- **Canela Text** is a commercial font (Colophon Foundry), not available on Google Fonts or any public CDN without a license. Per Axel/Julia, rather than leave it falling back to generic Georgia, **Fraunces** (a free, visually similar Google Font) now loads as an interim stand-in. `'Canela Text'` stays first in the font-family stack so a real license (self-hosted `.woff2` + `@font-face`, or an Adobe Fonts/Typekit embed) would take priority automatically with no further code change.

## 9. Generate/Upload button behavior (iterated three times)

**Round 1:** the title-bar "Generate Recap Doc" button previously disappeared entirely whenever any eligibility condition failed, with no explanation. Changed to always render; a new `recapDocDisabledReason` (string | null, replacing the old boolean `canGenerateRecapDoc`) drives whether it's the normal amber button or a grayed-out one with an explanation, in priority order: already has a doc → appointment type missing → not a first-consultation appointment → no Favorite Styles/Customization Requests to include.

**Round 2 (per Julia):**
- The Recap Doc field's own "+" upload button now shares the exact same `recapDocDisabledReason` gray-out behavior instead of its own narrower, unexplained disabled condition.
- The title-bar Generate button now disappears entirely once a Recap Doc actually exists (`hasRecapDoc`) — reversing that one specific case back to "hidden," since the inline thumbnail next to the Recap Doc field is the only affordance needed at that point.

**Round 3 (per Julia):** the explanation tooltip was originally a native HTML `title` attribute, which only ever triggers on hover. Julia wanted it to appear only on click. Since a truly `disabled` button never fires `onClick` at all, both buttons dropped the `disabled` attribute (keeping only the gray styling) and added a small `useClickTooltip()` hook — a visible flag that turns on for ~2.5s when triggered — rendering a small absolute-positioned message under the button instead of relying on hover.

## 10. Dynamic per-environment attachments-form URL

**Problem:** the URL used to open the external attachments-upload form (for Recap Docs, Measurement/Appointment Photos, and Customization Proposals) was a single hardcoded string that could only ever be correct in one environment — sandbox and production need genuinely different URLs (same form page ID, different base ID), and regular Airtable records aren't synced between a base's sandbox and production copies.

**Fix:** `RecapApp` now resolves this live by looking up a `resources` table record (originally found live as `attachments_form`, later renamed by Julia to `attachments_form_url` for clarity — both changes were verified live against the base before updating the code) and reading its `url` field. Falls back to the old hardcoded URL only if that record can't be found. Threaded as an `attachmentFormUrl` prop from `RecapApp` down through `PostAppointmentModal` and `CustomizationModal` to every attachment-upload call site (`AttachmentSection` ×2, `ProposalPreviewModal`, `ProposalDetailModal`, `openRecapDocUploadForm`) — no module-level constant remains for this.

Also surfaced and left flagged (not silently "corrected"): the old hardcoded fallback URL's base ID doesn't match the sandbox `resources` record's own URL — worth Julia confirming whether that was ever intentional.

## 11. Automation script out of sync (attachment_router.js)

Testing the Recap Doc upload surfaced a guard-clause failure: `Guard clause: unknown type value "Recap Doc". Expected one of: Measurements, Appointment Photos, Customization Proposal, Signed Proposal.` The repo's `attachment_router.js` was already at v1.3.0 with full Recap Doc routing (`AppointmentsRepository`, `APPOINTMENT_TYPES`, the idempotent duplicate-guard) — the live Airtable automation was simply running a stale v1.2.0 copy that had never been updated with the repo's current script. Fix was operational, not code: re-paste the repo's current `attachment_router.js` into the live automation's script editor.

A related build error surfaced afterward in the *interface* editor — `Top-level await is not available in the configured target environment`. Traced to the automation script's content having been accidentally pasted into the Interface's code editor instead of the automation's own editor (automations support top-level `await`; browser-targeted Interface Extension bundles don't). Resolved by putting each file back in its correct editor (`recap.tsx` in the Interface, `attachment_router.js` in the Automation) — the two files' very different line counts (≈4,800 vs. ≈580) were noted as a quick way to sanity-check which is currently pasted where.

## 12. Consultation-appointment prefill (two attempts)

Once the automation was current, the real gap surfaced: the guard clause correctly rejected an upload because the Attachments record's `appointment` link field was empty — the form was prefilling the wrong (or no) target.

**Attempt 1:** Julia added two lookup fields on Clients — `consultation_appointment_time` and `consultation_record_id` — through a manually-curated "Appointment Records" link, so a Recap Doc always targets the client's designated first non-cancelled consultation appointment rather than whichever appointment happens to be open in the modal. The record-ID lookup was wired in as the form's `prefill_appointment` value. Same failure persisted.

**Diagnosis (Axel):** prefilling a "link to another record" field on an Airtable form matches the linked table's *primary field display text*, not a raw record ID. Appointments' own primary field is "Appointment Time." Code was switched to prefill with the lookup's formatted display text instead.

**Actual root cause (Julia, after retesting):** the "appointment" field had simply never been added to the upload form at all — nothing could have prefilled it regardless of which value was sent. Once the field was added to the form, and the `consultation_record_id` lookup (which Julia had deleted and recreated, yielding a new field ID) was re-verified live, the code was reverted back to prefilling by record ID — the more precise match, with a code comment left specifically noting the wrong "must be display text" theory so it doesn't get "rediscovered" later.

A "Consultation Appointment" read-only display row was also added to the appointment detail page, showing the resolved consultation appointment's time, so it's easy to confirm which appointment a Recap Doc will actually attach to before generating it.
